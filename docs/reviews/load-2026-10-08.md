# Backend load test — 8 October 2026

## Outcome

**The isolated backend handled 200 requests/second without errors or dropped arrivals. The 400 requests/second stage showed variability and needs a staging retest before being used as a capacity commitment.**

Across the staged and confirmation capacity runs, **26,994 workload requests reached the local API and all returned valid HTTP 200 responses**. The original 400-RPS stage failed the dropped-arrival threshold. A focused 30-second repeat passed the chosen targets, with 11,972 successful responses, about 399 completed requests/second, p95 92 ms, and 28 skipped arrivals (0.23%).

The small live check had no errors but p95 latency of about 981 ms from this machine. It was an availability/latency sample, not a live capacity test. No evidence here establishes the production API's maximum throughput or number of simultaneous viewers.

Initial stages ran for 20 seconds each; confirmation ran for 30 seconds. The initial 400 stage skipped 178/8,000 arrivals (2.23%) and therefore failed despite zero HTTP errors. The confirmation explicitly distinguished skip causes: **28 hit the 64-request in-flight cap; zero were skipped for scheduler lateness**. The original run did not split those counters, so the repeat cannot establish the cause of its earlier 178 skips.

The generator does not issue catch-up bursts. “Skipped” means a scheduled request was never sent, not an API error. This distinction prevents reporting fast HTTP responses as proof the entire offered load was served.

Pass targets: successful-response p95 <= 500 ms, error rate <= 1%, skipped arrivals <= 1%. These are initial engineering targets, not an agreed service SLA. The initial five-stage suite as a whole failed its final stage; the follow-up confirmation passed independently.

### Normal rate limiter

With application throttling intact, the 20-RPS mixed catalogue run stopped on its first HTTP 429 after 195 workload requests: 194 successful and one rejected, approximately 9.75 seconds into the run. The browse endpoint had received 100 workload requests, plus the discovery request. This matches the configured per-route/per-client budget of 100 requests per minute.

This is expected abuse protection, not evidence that the server can only serve 100 requests per minute globally. We did not bypass the live limiter. Capacity measurements used a guarded local bootstrap that disables the throttle only in the disposable test process.

### Live read-only smoke

- Target: `https://api.cinnetemple.com`.
- One discovery GET plus 30 workload GETs, paced at one per second; no authenticated requests or movie downloads.
- 30/30 valid HTTP 200 workload responses, zero errors, zero skipped arrivals.
- Median 525 ms; p95 981 ms; p99 1,207 ms.
- Browse p95 1,207 ms; search p95 599 ms; title detail p95 540 ms. Each route has a very small sample, especially title detail (six requests).
- Failed the provisional 500-ms p95 target. These times include client/network/TLS and server processing; no server-side timing trace was available to attribute the delay.
- Read-only Railway metadata showed one running backend instance in production and no staging environment. No live scaling or configuration changes were made.

## Environment and workload

One normally compiled NestJS process, PostgreSQL 16 and Redis 7. PostgreSQL used an isolated Docker tmpfs database with a Prisma connection limit of 10. Local Mac15,7 host: 12 logical CPUs and 18 GiB memory; Docker reported a 7.75-GiB VM memory limit. Other apps/containers were running, and the load generator shared this host with the backend/database. These resources are not equivalent to one Railway instance.

The catalogue contained 1,000 synthetic titles generated from demo data, with one synthetic user. Browse/detail used real database-backed repositories; search used the current Prisma substring implementation. Mix: 40% browse, 25% search, 20% title detail, 10% authenticated profile and 5% entitlement reads. The synthetic account had no purchases/entitlements. JWT verification was exercised; real sign-in, password hashing and refresh rotation were not part of this workload.

The discovery request selects titles visible in browse, so detail accesses cover a hot subset, not all 1,000 titles uniformly. Repeated queries and stages also warm caches. `NODE_ENV=test` uses pretty request logging rather than production JSON logging. API process samples reached approximately 305% CPU and 365 MiB RSS; CPU can exceed 100% across cores and this excludes separate logging/DB processes. These coarse samples are diagnostic, not a rigorous saturation profile.

## Findings and next steps

1. **Search has the clearest scaling concern.** `PrismaCatalogueRepository.search` fetches every published title and filters in application memory. During the 400-RPS confirmation, search p95 was 122 ms versus browse 87 ms. Move filtering/limits into indexed database search or use the existing OpenSearch driver, and benchmark with a realistic catalogue. This code path and timing make it a candidate for optimization, not proof it alone caused skipped arrivals.
2. **Browse fans out database queries.** Each request loads the hero and each configured category. Consider short-lived shared catalogue caching with explicit invalidation after admin edits, then measure its benefit. Do not cache user-specific entitlement responses globally.
3. **The live/local latency difference needs tracing.** Measure application handler time, database query time and client-network time in staging/production before choosing an optimization. Local throughput does not establish why live requests take around half a second at low load.
4. **Load balancing remains useful for availability**, but this test does not demonstrate that the current production instance is CPU-saturated. Fix the security findings and shared rate-limit/session behavior before horizontal scaling. Validate DB connection budgets and shared object storage, then test two replicas on deployment-equivalent hardware.
5. Establish staging and repeat from a separate load generator, with production-like resources and data distributions. Add a longer soak, database failover, replica failover, login/refresh concurrency, checkout/webhook idempotency and separately provisioned upload/encoding tests. CDN/HLS segment delivery requires its own streaming workload; API requests/sec cannot be translated into concurrent film viewers.

A local build issue was also encountered: `nest build` deleted `dist` while a retained TypeScript incremental cache prevented outputs being regenerated. The load setup uses `tsc --incremental false` to produce a fresh executable. The normal production build configuration was not changed by this task.
