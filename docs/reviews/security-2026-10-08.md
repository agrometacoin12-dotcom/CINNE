# Security review — 8 October 2026

**Result: remediation is needed before treating this build as release-ready.** The most important issues are account preclaiming during social login, incomplete Apple purchase authorization, persistent sessions after password reset, and payment configurations that fail open.

This reviews the current working tree, including the earlier uncommitted mobile, TV and HLS changes. It does not certify the deployed service or every device as secure. No production exploit requests, account changes, purchases, secret retrieval or deployment were performed for this review. Application behavior was reproduced offline with fixture users and mocked persistence/provider boundaries; dependency metadata was queried online.

### SEC-01: Account preclaiming survives verified social login

**Locations:** `apps/backend/src/modules/auth/google-oauth.service.ts:148`, `apple-auth.service.ts:119`, `users/users.repository.ts:113`, `auth/auth.service.ts:72`, `common/guards/admin.guard.ts:47` (paths under `apps/backend/src/modules` except the guard).

A person can register someone else's email with their own password. With the default email-verification setting, that account is immediately usable. When the real owner subsequently signs in with verified Google/Apple identity, `resolveUser` links the provider to the existing email account. It leaves the existing password and sessions intact. The person who preclaimed it retains access to the real owner's account.

The earlier admin-bootstrap fix is incomplete in this scenario: after the legitimate owner links a provider, `AdminGuard` sees a federated credential on the shared account. A password login or existing token belonging to the preclaimer can then pass the bootstrap check when the email is in `ADMIN_EMAILS`. This requires preclaiming an unused address before its owner uses social login; it does not bypass ownership of an already secured account directly.

**Reproduction:** fixture Google linking retained the preclaimed password, and the real AdminGuard subsequently granted the fixture principal bootstrap access. The corresponding Apple branch has the same linking behavior. No Google/Apple account was attacked.

**Fix:** require proof of email ownership for password registration. Avoid silently merging accounts solely by email. For legacy unproven accounts, require a recovery/linking ceremony that invalidates old credentials and sessions. Prefer explicit DB-admin provisioning over email-based privilege bootstrap. Also require verified provider email on the new-account branch, not only when linking an existing account.

### SEC-02: Apple purchase verification lacks product authorization

**Locations:** `apps/backend/src/modules/commerce/commerce.service.ts:65`, `drivers/apple-iap.verifier.ts:89`; `apps/ios/CinneTemple/Core/Commerce/TicketStore.swift:33`.

Apple signature, bundle and environment checks are present. However, `confirmApple` accepts any verified product from this app for any requested published title. The iOS app selects from 20 price-tier products, but the server does not validate that selection. A modified client can submit an unused cheap-tier transaction for a more expensive movie. The purchase record then reports the requested movie's price, not the verified transaction's actual economic value.

The verifier also drops fields needed for account binding and refund/revocation policy. There is no `appAccountToken` check. A copied, unused transaction could be claimed first by another account; transaction-ID deduplication prevents later reuse but does not establish its rightful buyer. Refund/revocation handling needs a separate lifecycle check, not just certificate validation.

**Reproduction:** an injected verifier returning a legitimate-shaped tier-1 result caused the real commerce service to grant an expensive fixture title. This isolates missing authorization after verification; it does not claim to have forged Apple's signature.

**Fix:** maintain a server-owned tier/product mapping, enforce the required tier for the selected title, and bind transactions to the authenticated buyer using `appAccountToken`. Enforce allowed purchase type, revocation/refund policy and transaction ownership. Make confirmation idempotent for the same buyer and intended purchase. Test tier mismatch, account mismatch, revocation, replay and concurrent confirmation.

### SEC-03: Resetting a password leaves compromised sessions alive

**Locations:** `apps/backend/src/modules/auth/auth.service.ts:206`, `users/users.repository.ts` (`updatePassword`), `auth/tokens.service.ts:89`.

Reset updates the password hash and user version but never revokes Session rows. The JWT/refresh implementation does not use that version to invalidate existing credentials. An attacker holding a refresh token can continue obtaining new access tokens after the owner resets the password. Rolling refresh can prolong that access until explicit session revocation or account suspension.

**Reproduction:** the actual reset path updated an Argon2 hash without invoking any session revocation. The rotation path checks expiry/status but not password-change time or security version.

**Fix:** atomically update the password/security version and revoke every prior session. Enforce the security version or a session revocation check for existing access tokens where immediate invalidation matters. Apply the same policy to both local and Cognito reset paths.

### SEC-04: Refresh rotation is not an atomic single-use operation

**Location:** `apps/backend/src/modules/auth/tokens.service.ts:89–123`.

Rotation reads an unrevoked session, unconditionally updates it by ID, then creates a successor. Two requests can both read the valid row before either revokes it; both issue token pairs. This weakens replay protection for stolen refresh tokens. Client-side single-flight logic cannot enforce server-side single use.

**Reproduction:** two concurrent calls with one fixture refresh token produced two distinct successor refresh sessions.

**Fix:** claim the existing session with a conditional atomic update including `revokedAt: null` and expiry; require exactly one affected row. Create the successor in the same transaction and track token families if replay detection should revoke the family. Add a real database concurrency regression test.

### SEC-05: Old JWTs retain removed privileges

**Locations:** `apps/backend/src/modules/auth/strategies/jwt.strategy.ts:30`, `common/guards/admin.guard.ts:47`, `modules/admin/admin.service.ts:291` and `:326`.

The JWT strategy returns token claims without consulting current account status, roles or user security version. AdminGuard trusts the token's admin role immediately. Role removal or suspension changes the database but does not invalidate a previously issued JWT. A demoted administrator can keep exercising admin privileges for the remaining access-token lifetime (15 minutes by default). Refresh correctly refuses suspended users, which bounds this particular window but does not close it.

**Fix:** check authoritative status and roles for privileged actions, or enforce a security-version/revocation cache updated on changes. Include suspension, demotion and logout tests with already issued access tokens.

### SEC-06: Payment configuration fails open

**Locations:** `apps/backend/src/config/env.validation.ts:53`, `modules/commerce/drivers/payment-driver.provider.ts:14`, `mock-payment.driver.ts:40`, `paystack-payment.driver.ts:23` and `:79`; `infrastructure/cdk/bin/app.ts:22`, `lib/api-stack.ts:159`.

Two separate unsafe configurations are accepted:

- Omit `PAYMENT_DRIVER` in production and it defaults to mock. The mock driver always reports payment success and accepts webhook signatures unconditionally. CDK also defaults to mock unless overridden. Tickets and coin credits can then be obtained without real settlement.
- Select Paystack with an empty secret and startup merely logs a warning. The webhook verifier uses the empty string as its HMAC key, so its signature can be generated by anyone. Existing pending purchase/top-up references can be fraudulently settled. Initialization with the missing key normally fails, so this is conditional on usable pending records or a misconfigured existing environment.

**Reproduction:** production env validation accepted default mock; mock verification returned paid; the actual Paystack verifier accepted an HMAC generated with the empty key.

**Fix:** production startup must reject mock payments and missing/invalid provider credentials. The webhook driver must independently fail closed when unconfigured. Settlement should require all provider amount/currency fields rather than treating missing values as acceptable. Test configuration combinations and webhook rejection. Actual production settings were not inspected.

## Further risks and hardening

| Surface | Finding and boundary | Recommended change |
|---|---|---|
| Email OTP — Medium | `auth/verification.service.ts:32` uses six-digit codes with a 15-minute TTL, no per-account attempt budget, and separate GET/DEL. Routes have global IP throttling but no account-wide limit; distributed attempts bypass that boundary, and concurrent correct submissions can both succeed. | Atomic compare-and-consume; per-account/purpose attempt budget and issuance limits. Redis/shared rate-limit state across replicas. |
| Signed media — design limitation | `media/media.controller.ts:76` authenticates only signed URL fields. Signing `u` prevents changing the ID but does not authenticate whoever presents the whole URL. The complete URL remains shareable. HLS URLs likewise behave as bearer credentials. The old audit's “fixed” statement overstates viewer binding. | Document bearer behavior accurately; use bounded playback leases, short expiries and entitlement revalidation for stronger control. DRM is required for stronger copy protection; signatures alone cannot provide it. |
| Original media expiry — Medium | `media.service.ts:383` creates a fresh full-TTL storage URL when redirecting. Redeeming an API link near expiry can extend access by another storage TTL; neither step rechecks ticket status. | Cap downstream expiry to the remaining playback lease and validate the lease when minting downstream access. |
| Android — Low, local compromise | `core/auth/TokenStore.kt:50` persists refresh tokens in ordinary Preferences DataStore, unlike iOS Keychain. Android's app sandbox and disabled backups help, but the file is not independently Keystore-encrypted. | Encrypt long-lived credentials using a Keystore-backed key. Review rooted-device/data-extraction threat model. |
| Desktop Studio — Low, environment-dependent | `electron/main.ts:132` saves raw token JSON when OS encryption is unavailable, without restricting this fallback to development. | Fail closed or use memory-only sessions in production when secure storage is unavailable; handle Linux insecure storage backends explicitly. |
| Web/TV/landing — hardening | Long-lived refresh credentials live in localStorage. A same-origin script compromise can read them. No exploitable script injection was established in this pass; TV dynamic text uses escaping and URL scheme checks. | Reduce persistence/lifetime, strengthen CSP and origin restrictions, and consider a BFF with HttpOnly cookies for web. Evaluate supported secure storage/device-link approaches on TVs. |
| Web navigation — Low | `AuthExperience.tsx:27` accepts any `next` starting with `/`, including protocol-relative `//host` destinations. | Parse and constrain destinations to the application's origin and reject backslashes/protocol-relative forms. Verify with a browser regression test. |
| TV transport — Low, content/configuration-dependent | `apps/tv/src/core.js:11` and the CSP permit HTTP media and requests. Default API build configuration uses HTTPS, but configured/catalogue HTTP media can still be intercepted. | Require HTTPS in release packages, allowing local development exceptions explicitly. |
| AWS realtime — Medium if deployed | `realtime-stack.ts:53` installs no connect authorizer; `lambdas/realtime/index.ts:30` stores anonymous connections. This exposes connection/storage cost and has no authenticated user routing. No private-message disclosure path was established. | Authenticate connect, reject missing identity, enforce quotas and wire identity-based delivery. |
| AWS data tier — hardening | Redis has TLS and isolated subnets, but no AUTH/ACL configuration and ingress from the entire VPC CIDR. Postgres ingress also trusts the VPC CIDR. | Restrict ingress to service security groups and configure Redis authentication. |
| API availability — hardening | `main.ts:91` gives all requests a two-hour body timeout. Global rate limiting is per process; multiple replicas don't share budgets. | Short general request deadlines, a separate large-upload path, and shared rate limiting. Confirm proxy/IP trust configuration. |

## Dependency scan

- **198 unique advisory entries:** 4 critical, 104 high, 75 moderate, 15 low.
- pnpm's aggregate metadata reports **208 findings:** 4 critical, 109 high, 80 moderate, 15 low. Multiple installed versions/paths make that total differ from the unique advisory count.
- These are package advisories, **not 198 confirmed exploitable application vulnerabilities**.
- Full advisory/version details with representative dependency paths are in [dependencies.json](security-2026-10-08/dependencies.json).

Priority triage:

1. **Next.js 14.2.35** has critical advisories for Windows-hosted servers and AVIF image optimization. This repo uses `output: 'export'` and `images.unoptimized: true`, so those server-side paths are not exposed by its intended static deployment. Upgrade anyway, but do not label the static site as confirmed remotely exploitable from this scan. The [image advisory](https://github.com/advisories/GHSA-2xp9-vwfh-vxw4) lists patched branches 15.5.24/16.3.3; select a currently supported release and re-audit after migration.
2. **proxy-addr 2.0.7** is in backend Express dependency paths. Its [critical advisory](https://github.com/advisories/GHSA-jqcg-44mw-7w3h) concerns trust-subnet/IP handling. This source does not explicitly configure Express `trust proxy`, so that attack precondition was not established; review actual ingress configuration and update through compatible parents.
3. **tar 6.2.1** is in desktop Electron build tooling. Its [critical parse/decompression advisory](https://github.com/advisories/GHSA-23hp-3jrh-7fpw) is a build/archive-input concern here, not an exposed backend upload parser. Update the build dependency chain.
4. **Electron, Vite, Nest/Express transitive dependencies, Multer and image/build tooling** have additional high advisories. Upgrade parent packages in tested groups. No multipart Multer controller usage was found; its installed presence alone does not prove a reachable multipart denial-of-service endpoint. Avoid blindly forcing transitive major versions with overrides.

Android release dependency resolution succeeded. OSV querybatch checked **174 resolved Maven coordinates** and **8 pinned iOS Git commits**; no matches were returned. This is limited by OSV package/commit coverage and does not establish absence of vulnerabilities in platform SDKs, native binaries or undocumented dependencies. Inventory/results: [native-dependencies.json](security-2026-10-08/native-dependencies.json).

No container image/OS-package scan was completed. The deployed Node, FFmpeg, operating-system and TV firmware builds were not inventoried.

## Remediation sequence

1. Close account preclaim/linking and bootstrap-admin exposure; invalidate sessions/credentials affected by unsafe historical linking as part of a reviewed migration.
2. Enforce production payment configuration and Apple product/account authorization.
3. Make reset, privilege changes and refresh replay invalidate access correctly; add concurrency and recovery regression tests with a real test database.
4. Update dependency groups and re-audit/rebuild backend, web and Studio.
5. Add OTP account limits, tighten media leases, secure local token persistence and harden deployment boundaries.
6. Validate actual production settings and release artifacts, then test physical Android/iPhone/LG/Hisense devices. This pass did not change or deploy application security behavior.
